# Issue list

Resolved findings from the 2026-07-18 audit are recorded in [`docs/reviews/review-resolution-v0.1.2.md`](docs/reviews/review-resolution-v0.1.2.md).

## Correctness and trust work

- [x] Replace heuristic compiler-output matching with structured `go test -json` event classification and explicit build diagnostics. `internal/runner.GoTest` now classifies from the `-json` event stream: a package-level `[build failed]` marker (the tool's own FAIL-summary line, emitted identically for compile *and* vet failures) means INVALID; a package that fails before any test starts for a non-build reason (init() panic, `TestMain` calling `os.Exit`, ...) means KILLED with no test attributed; a test still "started" when the stream ends (an unrecovered panic in a goroutine the testing package doesn't supervise, which aborts the binary without a clean per-test fail event) is attributed as responsible. The previous English-substring regex is kept only as a last-resort fallback for the rare case where `go test` rejects the invocation before `test2json` ever writes JSON (e.g. build constraints exclude all Go files). This also fixed a latent attribution bug: the old `--- FAIL: ` line regex was anchored to line-start and silently missed every subtest name, since Go indents nested subtest result lines (`    --- FAIL: TestX/sub`) — a common table-driven-test pattern. "killed by" now correctly includes subtests.
- [x] Add process-signal tests proving temporary-workspace cleanup under abrupt CLI termination. Found and fixed a real bug in the course of this: `cmd/mutation-judge/main.go` used bare `context.Background()` with no signal handling, so Go's default disposition for an unhandled SIGINT/SIGTERM is immediate process termination — deferred sandbox cleanup never ran, confirmed by reproduction (a real `SIGTERM` left the temp sandbox on disk). Fixed with `signal.NotifyContext`, a distinct `exitInterrupted = 130` exit code, and `cmd/mutation-judge/main_test.go`'s `TestSIGTERMCleansUpTemporarySandbox`, which sends a real `SIGTERM` to a real subprocess and checks the sandbox is gone; verified the test fails against the reverted (buggy) code.
- [x] Add a fixed external corpus evaluation with manually reviewed survivors. See `docs/evaluation.md`, "External corpus evaluation" (2026-08-18): three dependency-free real-world libraries (`rs/xid`, `dustin/go-humanize`, `google/uuid`), same bounded operator set, every survivor traced to source. Found two provably equivalent mutants (via a discarded return value and a no-op string replace), several genuine boundary/coverage gaps, and one real bug in `google/uuid`'s own test suite (`TestNullUUIDUnmarshalText` never calls `UnmarshalText`).
- [x] Test cgo, build tags, package initialization failures, custom `TestMain`, and unusual toolchain failures. Added four end-to-end fixtures under `tests/integration/testdata/` (invisible to `./...` expansion): a real cgo package, a build-tag-excluded file proving discovery only mutates what `go list`'s `GoFiles` includes, an `init()` panic (classified KILLED, not INVALID), and a custom `TestMain` calling `os.Exit` before `m.Run()` (classified KILLED with no test misattributed).
- [x] Decide whether publication builds should use full TOML/YAML libraries instead of the documented strict flat subset. Decided: keep the strict flat subset permanently; do not adopt a dependency. See `docs/decisions/0001-config-parser-scope.md` for the full reasoning. Implemented the one concrete improvement the decision pointed to: YAML's native block-list style is now accepted for list-valued keys (`internal/config/config.go`, `readYAMLBlockList`), since it's unambiguous to parse without adopting general nested-YAML parsing.
- [x] Add an explicit warning/evidence field for non-fatal cache write failures. A cache write failure (e.g. a full or unwritable `cache_dir`) was previously silently discarded (`_ = store.Put(...)` in `internal/analysis/analysis.go`), so a person could have no idea caching had stopped working. Now surfaced three ways, deduplicated into one summary message rather than one line per mutant: a new `model.Report.Warnings` evidence field (present in JSON, `omitempty` when empty), a `warnings` section in the text and HTML renderers, and a `warning:` line on stderr. The mutant's own result is unaffected and the run still succeeds — this is explicitly non-fatal. Verified end-to-end against a real blocked cache directory (a regular file where the cache directory should be, which fails reliably regardless of user privilege, unlike a permission-bits approach) via both a unit test (`TestCacheWriteFailureIsReportedAsWarningNotFatal`) and the built CLI binary in all three output formats.
- [x] Add differential fixtures comparing source replacements with manually authored mutants, and expand precedence/parenthesization regression tests for complex boolean expressions. `internal/frontend/differential_test.go` reconstructs the full mutated source for a discovered mutant and byte-compares it against a hand-verified expected string (verified against real `Discover` output before being written down, not hand-calculated), then confirms it still parses as valid Go. Covers `&&`/`||` mixed precedence, left-associative `&&` chains at multiple depths, `!(...)` double-parenthesization (a real, notable finding: `!(a && b)` mutates to `((a && b))`, since the NOT operand is itself a `ParenExpr` whose source already includes its own parens), and boundary comparisons nested inside a boolean tree. Verified the fixtures have teeth by deliberately breaking the parenthesization logic: 4 of 8 failed immediately with a clear diff.
- [x] Add a persistent journal/log entry for abnormal process termination, for post-mortem debugging beyond the exit code and partial report. `cmd/mutation-judge` now appends one NDJSON entry to `.mutation-judge/journal.ndjson` (independent of `--no-cache`) on every SIGINT/SIGTERM: timestamp, which signal specifically (SIGTERM usually means an orchestrator/CI timeout, SIGINT usually means a person), which phase (baseline vs. mutant execution), patterns, operators, and — for the mutant-execution phase — how many mutants had already completed. A journal write failure is itself non-fatal (surfaced on stderr, doesn't change the exit code), matching how the cache-write-warning item above is handled. Signal identity capture required replacing `signal.NotifyContext` with an explicit `signal.Notify` + buffered-channel handoff (`NotifyContext` doesn't expose which signal fired); verified race-free via the channel send happening-before the `cancel()` call. Verified end-to-end with real `SIGTERM` and `SIGINT` against the real binary, plus two permanent regression tests (`TestSIGTERMWritesBaselinePhaseJournalEntry`, `TestSIGTERMWritesMutantsPhaseJournalEntry`) — the latter synchronized off mutation-judge's own `--progress` output rather than a sleep guess, so it reliably lands mid-mutant-execution on any machine speed.
- [x] Fix a real platform-dependent misclassification in `internal/runner.classifyEvents`, found via a genuine `go test ./...` run on macOS (not this development environment, which is Linux): "build constraints exclude all Go files" produces zero JSON events on Linux (correctly handled by the pre-existing fallback path), but on the reporting platform `go test -json` instead emits a package-level `FAIL <pkg> [setup failed]` line — a different bracketed reason word than the `[build failed]` marker the classifier only checked for — so it fell through to KILLED instead of INVALID. Fixed by matching the general `FAIL <pkg> [<reason>]` structure instead of one hardcoded phrase. Added direct unit tests against `classifyEvents` with synthetic events (`TestClassifyEventsRecognizesSetupFailedMarker` reproduces the exact reported scenario verbatim; `TestClassifyEventsRecognizesUnknownReasonWordInFailBracket` proves the fix generalizes rather than adding a second hardcoded phrase) rather than relying only on a real toolchain's platform-specific behavior, which is what let this slip through the original integration-only test the first time. Confirmed both new tests fail against the reverted substring-only check. **Confirmed fixed on the reporting macOS machine itself**: full `go test ./... -count=1` (all 18 packages, including `internal/runner`) and `examples/run-all.sh` both clean on a rerun against the fix.
- [x] Fix a multi-package misclassification in `internal/runner.classifyEvents` that inflated the mutation score on exactly the default invocation shape (`mutation-judge ./...`): `testEvent` decoded no `Package` field, so once *any* test anywhere in the merged `go test -json` stream started, a single global `sawRun` flag suppressed the INVALID verdict for a completely different, unrelated package that failed to build in the same run — turning an uncompilable mutant into a counted KILL. `--narrow-test-scope` incidentally masked this for packages with no dependents (the mutant then ran scoped to just its own package), which is why it went unnoticed even though it's the *default* (unscoped) path that's broken. Fixed by decoding `Package` and tracking, per package rather than globally, whether it started any test of its own and whether it produced the package-level `FAIL <pkg> [<reason>]` summary line: a package that emits that marker and never starts a test of its own is INVALID regardless of whether sibling packages in the same pattern set ran their own tests to completion; an actual test failure anywhere still wins as KILLED. Added two direct `classifyEvents` unit tests with synthetic two-package event streams (`TestClassifyEventsPackageBuildFailureIsInvalidEvenWhenSiblingPackageRuns` for the bug itself, `TestClassifyEventsRealFailureElsewhereStillWinsOverBuildFailure` proving the fix doesn't overcorrect into hiding a genuine kill), a `GoTest.Run`-level test against a real two-package module with patterns `./...` (`TestGoTestClassifiesCompileFailureAsInvalidAcrossPackages`), and an end-to-end CLI fixture (`tests/integration/testdata/multipkg`, `TestMultiPackageCompileFailureIsInvalidNotKilledEndToEnd`) mutating a compile-invalid arithmetic mutant — the same documented case as `examples/arithmetic` — while an unrelated sibling package's own passing test runs alongside it. All single-package existing tests (compile failure, vet failure, init-panic-as-KILLED, async-goroutine-panic attribution, build-constraint exclusion) traced by hand to confirm the per-package refactor preserves their behavior exactly.
- [x] Fix the cache key binding the wrong Go version. `cache.Key` and the top-level report both used `runtime.Version()` — the toolchain that happened to compile the mutation-judge binary itself — as a stand-in for the toolchain that actually builds and runs a mutant's tests. The two are ordinary to disagree: a cross-compiled CLI, or simply the `go` on PATH being upgraded or downgraded after the binary was built, both leave `runtime.Version()` unchanged while vet/language/runtime behavior underneath it can differ — so a cache entry from before such a change kept getting reused after it, a stale, silently wrong verdict. The wrong value was in the key *twice* over (a bare `runtime.Version()` argument, and again via `GoTest.Version()` feeding `backendVersion`), and GOOS/GOARCH/CGO_ENABLED/GOFLAGS — every one of which can also change what a mutant compiles to or how it behaves — were entirely absent from the key. Fixed by adding `runner.DetectToolchain`, which execs `go env GOVERSION GOOS GOARCH CGO_ENABLED GOFLAGS` once per analysis run (not once per mutant) and is used for both the cache key (replacing the bare `runtime.Version()` argument with `ToolchainInfo.Key()`, folding in all five variables) and the report's own `go_version`/`bounds` fields; `GoTest.Version()` now reads `go env GOVERSION` directly instead of `runtime.Version()` too, closing the second, redundant occurrence in the key. `runtime.Version()` no longer appears anywhere in this codebase's production code. A missing `go` on PATH is now caught immediately at the start of `Analyze` (via `DetectToolchain`'s own error) rather than only later once baseline execution fails. Added unit tests for the new primitives (`TestDetectToolchainReadsInvokedGoNotRuntimeVersion`, `TestDetectToolchainMissingGoIsAnError`, `TestGoTestVersionMissingGoIsUnknownNotRuntimeVersion`, `TestToolchainInfoKeyDistinguishesEveryField`), and the permanent end-to-end regression the doc suggested: `TestCacheKeySensitiveToGoToolchainChange`, which runs `Engine.Analyze` twice with identical source/mutants/config but a fake `go` wrapper on PATH reporting two different `GOVERSION` values across the two runs (every other real toolchain invocation `prepare()` needs — `go env GOMOD`, `go list ...` — is forwarded to the real `go` binary unchanged), and asserts the second run is a cache miss rather than a hit.

## Performance work

- [x] Measure source-tree digest and full-sandbox copy cost on large modules before narrowing either correctness boundary. See `docs/performance.md` and `internal/workspace/workspace_bench_test.go`. `Digest` (read-only) scales cleanly and is inexpensive even at 8000 files (~24MB source, ~100ms). `CopyModule` (write-heavy) is both the more expensive operation and, on the constrained single-vCPU sandbox this was measured on, subject to substantial run-to-run storage I/O variance that swamped any clean scaling signal — repeating the identical input size across separate invocations produced results differing by more than 2x. This does not support narrowing what gets copied (even the worst observed cost is a one-time overhead almost certainly dwarfed by the baseline `go test` run that follows on any project large enough to have thousands of files), but it does support prioritizing the next item below, since it targets exactly the write path shown here to be both the more expensive and the more variable one.
- [x] Explore copy-on-write/reflink sandbox creation where the host filesystem supports it. Implemented for Linux (`internal/workspace/reflink_linux.go`, the `FICLONE` ioctl, defined as a stable kernel ABI constant — no new dependency), always falling back to the existing full copy on any failure, so this is purely additive and never a correctness risk even where it doesn't engage. Verified in this environment: the fallback path (via a new `TestCopyModuleProducesIndependentCopy`, which didn't exist before — `CopyModule` had previously only been exercised indirectly), and `tryReflink`'s failure paths never leave a partial file behind. **Not verified in this environment**: the actual clone success path, despite a genuine attempt (installed `xfsprogs`/`btrfs-progs`, created a correctly-sized reflink-enabled XFS image) — this container's kernel has neither XFS nor Btrfs support and can't load modules, confirmed via `dmesg`. `TestTryReflinkClonesOrCleanlyDeclines` is written to verify the critical isolation property (a write to the clone must never reach the original) but honestly `t.Skip()`s here rather than silently passing; would be genuinely useful for someone with real btrfs/xfs access to run. macOS's `clonefile(2)` equivalent is deliberately deferred — see `internal/workspace/reflink_other.go` for the three options considered (cgo, a new dependency, or an unverifiable raw syscall) and why each was declined for now, directly informed by the `classifyEvents` lesson above: this project has no way to test macOS-specific behavior, and a filesystem syscall is a much higher-stakes place to ship that blind than a text classifier was. See `docs/performance.md`.
- [x] Add coverage-guided package/test sharding. Implemented as **dependency-graph**-guided rather than coverage-guided — a considered choice, not a shortcut; see `docs/performance.md` for why plain `-coverprofile` data can't safely narrow per-mutant scope without much heavier per-test-attribution machinery, while the module's own import graph (asked of `go list -deps -test` directly, not walked by hand) has no such ambiguity. Opt-in via `--narrow-test-scope` (default off): any uncertainty — the mutant's package can't be resolved, or no scope was computed for it — falls back to the full pattern set rather than risking a false SURVIVED. The critical correctness property (narrowing can never miss a real kill) is proven end-to-end against `tests/integration/testdata/scoping`, a fixture built specifically to break a naive implementation: a mutant in package `a` is caught only by package `d`'s *external* test file, which imports `a` in a way no plain build-`Imports` walk would see — confirmed still correctly KILLED with scoping on, plus a non-flaky timing signal (an unrelated package with a deliberately slow test) proving scoping actually excludes it rather than safely doing nothing. Found and fixed a related, genuine pre-existing gap while building this: `cache.Key` never included which test patterns were actually used for a mutant, a latent staleness risk this feature made more likely to matter; fixed independently of whether scoping is enabled.
- [x] Add parallel isolated workers with deterministic output ordering. Opt-in (`--workers N`, default 1 — sequential, unchanged from every earlier version). Each worker gets its own fully independent sandbox, so concurrent execution is safe: a review of `cache.Store` (stateless), `workspace.Apply`/`CopyModule` (no shared mutable state), and `coverage.Map.Covered` (read-only during execution) confirmed this *before* any concurrent code was written. Real throughput can't be measured on this development environment's single vCPU, and none is claimed — but correctness fully can be, via Go's race detector (which catches races through goroutine interleaving regardless of core count) and is: `go test ./... -race` is clean, including 8 repeated runs of the parallel-specific tests to catch anything intermittent. Determinism is proven directly (`TestParallelExecutionIsDeterministicAcrossRuns`, three runs with an artificially-varied-delay fake backend, identical order every time), as is equivalence with sequential execution against both a fake backend (`TestParallelExecutionMatchesSequentialResults`) and the real toolchain (`TestWorkersProducesSameResultsAsSequential`), plus cancellation and hard-error-propagation tests. **Found and fixed a real, independent bug while verifying this feature** (not while building it): adding a `workers` key to `Config.AsMap()` for `--print-config` visibility silently widened the cache key to be sensitive to worker count too, since the cache key had been built from the full `AsMap()` — running the same analysis with a different `--workers` value produced zero cache hits despite no mutant's actual outcome being affected. Fixed with an explicit, minimal `cacheRelevantConfig` subset (exactly `Timeout`/`TestRun`, the only two `Config` fields that reach a mutant's `go test` invocation); confirmed the regression test fails against the reverted code. See `docs/performance.md`.
